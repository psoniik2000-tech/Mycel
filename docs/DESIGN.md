# Mycel — дизайн-документ

> Версия 0.1 · 2026-11-06 · статус: черновик для обсуждения

**Mycel** (от «мицелий» — грибница) — мессенджер для небольшой закрытой группы (до 50 человек), которому не нужен центральный сервер. Каждое устройство — полноценный узел сети: хранит свои данные, пересылает чужие зашифрованные сообщения и помогает остальным найти друг друга. Пока жив хотя бы один путь между двумя участниками, сообщение дойдёт: через интернет, через Tor, через локальную Wi‑Fi-сеть или через «флешку».

## 1. Цели и не-цели

### Цели

| # | Цель | Как достигается |
|---|------|-----------------|
| G1 | Нет обязательного сервера | P2P-сеть; любой узел может быть ретранслятором и «почтовым ящиком» |
| G2 | Устойчивость к блокировкам | Нет доменов и фиксированных IP; несколько транспортов, маскировка трафика, работа в локальной сети без интернета |
| G3 | Сквозное шифрование всего | MLS для групп, Double Ratchet для личных чатов, шифрование файлов и локальной базы |
| G4 | Телефон и ПК | Общее ядро на Rust + UI на Tauri 2: Windows, Linux, macOS, Android (iOS — с оговорками, см. §15) |
| G5 | Все типы контента | Текст, ответы, реакции, редактирование, файлы любого размера, фото, видео, голосовые, видеокружки, звонки |
| G6 | Быстро и экономно | Rust, QUIC, дедупликация медиа по хешу, докачка с нескольких пиров |
| G7 | До 50 человек | Сеть рассчитана на «все знают всех»; без глобального DHT и сложной маршрутизации |

### Не-цели

- Публичные каналы, поиск незнакомцев, тысячи пользователей.
- Анонимность уровня Tor «по умолчанию» (возможна как опция транспорта, но тормозит).
- Совместимость с Telegram/Matrix/Signal.
- App Store / Google Play (распространение — APK и установщики, см. §11).

## 2. Модель угроз

**От чего защищаемся:**

1. **Блокировка по DNS/IP/SNI.** Нет домена, который можно заблокировать; адреса узлов — домашние и мобильные IP участников, они меняются.
2. **DPI (глубокий анализ пакетов).** Трафик выглядит как обычный HTTP/3 (QUIC на 443) или как Tor-трафик через мосты obfs4/WebTunnel/Snowflake.
3. **Полное отключение мобильного интернета / «белые списки».** Работа через локальную сеть (Wi‑Fi, точка доступа с телефона), офлайн-передача пакетами через файл/QR.
4. **Перехват и чтение трафика.** Сквозное шифрование; ретрансляторы видят только шифротекст.
5. **Изъятие одного устройства.** Локальная база зашифрована; PIN/биометрия; forward secrecy — старая переписка не расшифровывается новыми ключами; удалённое исключение устройства из групп.
6. **Подмена участника.** Каждый участник — ключ Ed25519; проверка «кодов безопасности» по QR при личной встрече.

**От чего НЕ защищаемся полностью:**

- Анализ метаданных глобальным наблюдателем (кто с кем и когда соединялся) — частично снижается через Tor-режим.
- Взломанное (заражённое) устройство участника.
- Участник группы, который сам сливает переписку.

## 3. Общая архитектура

```
┌────────────────────────── Устройство (телефон или ПК) ──────────────────────────┐
│                                                                                  │
│   UI (Tauri 2 + SolidJS/TypeScript)   ── экраны, анимации, медиаплеер            │
│           │  команды / события (IPC)                                             │
│   ┌───────▼──────────────────────────── mycel-core (Rust) ─────────────────────┐ │
│   │  API: send_message, open_chat, upload_file, start_call, ...                │ │
│   │                                                                            │ │
│   │  mycel-sync   ── журнал событий, сверка множеств, store-and-forward        │ │
│   │  mycel-crypto ── MLS (группы), Double Ratchet (1:1), ключи устройств       │ │
│   │  mycel-media  ── блобы BLAKE3, чанки, превью, перекодирование, Opus        │ │
│   │  mycel-store  ── SQLite + SQLCipher, зашифрованные блобы на диске          │ │
│   │  mycel-net    ── транспорты: QUIC (iroh) · Tor (arti) · LAN (mDNS) · файл  │ │
│   └────────────────────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────────────────────┘
             ▲                     ▲                        ▲
             │ прямое P2P          │ через узел-ретранслятор │ локальная сеть
             ▼                     ▼                        ▼
       другие участники      «якорный» ПК участника      соседние устройства
```

### Роли узлов

Все узлы запускают один и тот же код, различается только режим:

| Роль | Кто | Что делает |
|------|-----|-----------|
| **Лёгкий узел** | Телефон | Отправляет/получает, хранит свою историю, отдаёт свои блобы, пока онлайн |
| **Якорь (anchor)** | ПК, ноутбук, Raspberry Pi, любой VPS участника | Работает 24/7: хранит зашифрованные сообщения для офлайн-участников (store-and-forward), является ретранслятором для тех, кто за жёстким NAT, раздаёт медиа |
| **Мост (bridge)** | Якорь с белым IP или за границей (опционально) | Принимает подключения из-под блокировок, может работать через Tor onion-сервис |

> Ключевая идея: «сервер» не нужен, но **якорь** очень желателен — это просто ПК одного из участников, который чаще включён. Якорей может быть несколько; если один пропал, работают остальные. Ни один якорь не может читать переписку.

## 4. Идентичность, устройства и приглашения

### 4.1 Ключи

- **Ключ пользователя** (`UserKey`, Ed25519) — «паспорт» человека. Хранится на первом устройстве, экспортируется только в виде зашифрованной резервной копии (фраза из 24 слов, BIP-39).
- **Ключ устройства** (`DeviceKey`, Ed25519) — у каждого устройства свой. Ключ пользователя подписывает **сертификат устройства**: «устройство X принадлежит пользователю U».
- **NodeId** в сети = публичный ключ устройства (так устроен iroh — адрес узла и есть его ключ, подделать нельзя).

### 4.2 Сообщество (Space)

Все 50 человек — одно **пространство** (Space). У пространства есть:
- список участников (подписанный журнал: кто, кем и когда добавлен/удалён);
- администраторы (могут приглашать и исключать);
- общий «служебный» MLS-канал, по которому расходятся адреса узлов и списки якорей.

**Режим «обычный мессенджер»** (выбор на первом экране, переключатель в Настройках; `src/simple.tsx`): своё скрытое пространство без вопросов о названии, видно только «Контакты» и личные чаты, общий чат и админство скрыты.

**Попарные контакты.** «Добавить контакт» в простом режиме даёт одноразовую ссылку `mycel://contact/<base32>` (секрет, адрес автора, relay); сделать её может любой, не только админ. Принявший получает от автора Welcome в новую MLS-группу на двоих (тот же протокол `mycel/join`, секрет помечен как контактный). Такая группа — «пространство на двоих» внутри того же узла:
- `space_id` её конвертов = первые 16 байт id группы, значит своя тема ящика и свой push-тег;
- конверты, Have-списки и адреса уходят только партнёру; участники пространства и другие контакты о ней не узнают и её шифртекст не хранят; партнёр не получает чужих адресов;
- допуск пиров (sync, блобы, звонки) = участник пространства **или** партнёр по контакту;
- чат — обычный 1:1 (`Chat = Some(партнёр)`), так что история, статусы, медиа и звонки работают без изменений; профиль (имя, KeyPackage) рассылается и в каждую пару.

Почему так, а не несколько узлов в процессе: N узлов = N iroh-эндпоинтов (портов, relay-соединений), N опросов ящика и переделка всего приложения под несколько открытых узлов (сейчас открыт один). Мультигрупповой узел — ~200 строк в `mycel-core` и пара команд в приложении: один эндпоинт и ящик на все контакты. Узел без пространства, принимая контактную ссылку, сначала создаёт своё (приложение считает «есть пространство» = «настроено»). Старые круги простого режима продолжают работать: их участники показываются в «Контактах» рядом с попарными.

### 4.3 Приглашение (onboarding)

1. Админ нажимает «Пригласить» → генерируется одноразовый **инвайт**: `mycel://join/<base32>`, содержит:
   - ID пространства и публичный ключ админа;
   - одноразовый секрет;
   - **список адресов для первого подключения** (NodeId + IP:порт якорей, onion-адреса мостов, ключи relay).
2. Инвайт передаётся как QR-код (лично) или текстом через любой канал (почта, другой мессенджер, бумажка).
3. Новый участник подключается к любому адресу из списка, доказывает владение секретом, получает членство и Welcome-сообщение MLS.
4. Дальше адреса обновляются автоматически по служебному каналу.

Так нет никакого «центрального сервера регистрации»: точка входа — любой живой участник.

### 4.4 Несколько устройств

Телефон и ПК одного человека — один **аккаунт**: для собеседников одно имя, один аватар, один чат и одна история; свои устройства видят все чаты и отправленное с соседних.

- **Аккаунт** = id первого устройства (корня). Старое устройство без привязок — аккаунт из одного устройства, ничего не меняется.
- **Подтверждение** — событие `Account` (вместо отдельного сертификата: события и так подписаны ключом устройства и аутентифицированы MLS). Корень шлёт `Account { account: себя, devices: [...] }`, привязанное — `Account { account: корень, devices: [] }`. Устройство D считается устройством аккаунта U, только если U перечисляет D **и** D называет U (никто не присвоит чужое устройство). Шлётся туда же, куда профиль (общий чат и каждый контакт), и заново, когда в какой-то группе прибавились участники. Последнее `Account` каждого автора хранится в meta `accounts`.
- **Привязка**: Настройки → «Устройства» → «Привязать устройство» на корне даёт одноразовую ссылку/QR `mycel://device/<base32>` (секрет, адрес, relay). Новое устройство вставляет её вместо приглашения (протокол `mycel/join`, KeyPackage last-resort). Корень одним коммитом на группу добавляет его в пространство и во все 1:1-группы (личные чаты и попарные контакты) и отвечает пачкой: Welcome пространства, (группа, партнёр, контакт?, Welcome) каждой 1:1-группы и история последних ~8 МиБ событий (подписи проверяются). Потом рассылает новый список `Account`; новое устройство копирует имя корня и шлёт своё `Account`.
- **Новые 1:1-группы**: создатель добавляет одним коммитом партнёра со всеми его устройствами и свои остальные устройства (KeyPackage из их профилей); принявший контактную ссылку добавляет свои устройства сам, Welcome уходит и в тему ящика своего пространства, которую соседи опрашивают. Коммиты в 1:1-группах принимаются от любого участника (в пространстве — только от админа).
- **Чат** 1:1 = `Some(аккаунт партнёра)`. Если чат начался по устройству, которое потом оказалось частью аккаунта, его события переносятся в чат аккаунта (`merge_chats`).
- **UI**: участники, авторы и звонки показываются по аккаунту; «моё» = любое своё устройство. Квитанция «прочитано» с любого своего устройства гасит непрочитанные на остальных. Пуш 1:1 — на все устройства получателя (`x-to` — список тегов).
- **Отвязать** (только корень): удаление из всех групп MLS и новый список `Account`; история, уже слитая в чат аккаунта, остаётся.

Ограничения (`shortcut:` в коде): привязывать и отвязывать может только корень и только как админ своего пространства (в простом режиме — всегда; в чужом сообществе нужен был бы админ); два одновременных коммита в одной 1:1-группе её разветвят; звонок 1:1 идёт на корень; код безопасности — по паре устройств; история до привязки — только то, что влезло в пачку.

### 4.5 Проверка подлинности

У каждой пары участников есть **код безопасности** (60 цифр / QR, производная от ключей пользователей). При встрече можно отсканировать — контакт помечается как проверенный. Смена ключа контакта показывается крупным предупреждением.

Сейчас (экран «Участники», значок щита): код — BLAKE3 (`derive_key`) от отсортированной пары device id → 12 групп по 5 цифр (`mycel_crypto::safety_code`), QR сканируется на Android. Отметка «Проверен» хранится локально (имя → код); если у участника с проверенным именем код другой (новое устройство/ключ) — отметка снимается, показывается предупреждение.

### 4.6 Имена пользователей и главный сервер

Основной способ пользоваться Mycel — **главный сервер** (`DEFAULT_SERVER`, позже VPS): установил, один раз зарегистрировал `@имя`, пишешь кому угодно по имени. Главный сервер — якорь, который для всех: relay, почтовый ящик (store-and-forward) и справочник имён (`crates/mycel-core/src/dir.rs`). Содержимое он не читает: конверты зашифрованы MLS, справочник лишь отдаёт по `@имени` подписанную контактную ссылку. Свои якоря и пространства по приглашениям — второй, необязательный режим («Другие способы»).

- **Ящик**: порт relay главного сервера отвечает тем же HTTP API, что `mailbox/worker.js` (`/box/…`; `/push/…` принимается и игнорируется — будить телефоны (FCM) остаётся воркеру), файлы `box/<topic>` в папке данных, 30 дней (`serverbox.rs`; своя hyper-петля: запросы ящика наши, остальное — `RelayServiceWithNotify`). `Opts::mailbox` может содержать несколько адресов через пробел: каждый конверт уходит в каждый, каждый опрашивается (у первого старые ключи `box_seq`). Приложение передаёт «ящик пользователя + главный сервер».

- **Запись**: (имя, отображаемое имя, *многоразовая* контактная ссылка `mycel://contact/`, ключ устройства, время) с подписью этого ключа, плюс аккаунт-владелец (§4.4) и, если пишет не корень, *сертификат устройства* — подпись корня над `("mycel-device", ключ устройства)`. Корень выдаёт его при привязке (4-й элемент пачки привязки, meta `devcert`; устройства, привязанные старой версией, привязать заново). Секрет многоразовой ссылки (meta `pubcontact`) не сгорает при использовании; повторно из той же пары контакт не создаётся.
- **Имя принадлежит аккаунту**: 5–32 знака `[a-z0-9_]`, без учёта регистра; кто первый — того и имя. Обновить или сменить имя может любое устройство того же аккаунта и только более новой записью (старое имя освобождается). Сервер проверяет подпись, что ссылка ведёт на этот ключ и сертификат. Ссылка в записи — того устройства, что писало последним; принявшему её это устройство одним коммитом добавляет в пару и остальные устройства аккаунта (§4.4), так что пишущий по `@имени` доходит до всех. `NameOf` ищет по аккаунту или по ключу устройства.
- **Протокол** `mycel/dir/1` (запрос–ответ postcard): `Register`, `Lookup(имя)`, `Search(префикс ≥ 2)` → до 20 (имя, отображаемое имя), `NameOf(ключ)`.
- **Запуск отдельно**: `mycel-anchor http://IP:PORT` (в релизе `mycel-server-*`) — только главный сервер, без пароля и пространства.
- **Сервер**: свой iroh-эндпоинт со стабильным ключом (`dir_key` в папке данных якоря, не пространства — смена пространства его не меняет), подключён к своему же relay через 127.0.0.1; записи — `directory.json` (одна блокировка на проверку и запись, запись через tmp + rename). Его id отдаёт порт relay по `GET /mycel-id` (своя петля приёма вокруг `iroh_relay::RelayService` вместо `Server`).
- **Клиент**: настройка «Сервер имён» = `DEFAULT_SERVER` (`http://5.130.50.199:3340`) или `url#id`. Без `#id` id берётся по HTTP и после первого успеха закрепляется в настройке (TOFU). Адрес главного сервера добавляется как relay в каждое пространство. Запись обновляется при каждом открытии (адреса меняются).
- **Интерфейс**: первый запуск — имя и `@имя` (личное пространство создаётся молча) или «Войти по QR или ссылке» (ссылка `mycel://device/` из «Настройки → Устройства → Добавить устройство» на уже вошедшем устройстве: аккаунт, имя, контакты и история по §4.4, `@имя` берётся через `NameOf`), старые пути — «Другие способы»; **несколько аккаунтов**: аккаунт = личное пространство («Личные чаты»), в простом режиме Настройки сверху показывают их список (отображаемое имя и `@имя` из localStorage этого пространства) и «Добавить аккаунт» (закрывает текущее, тот же первый запуск); у каждого своё `@имя`, чаты и заглушенные чаты; поиск в «Чатах» ищет и по справочнику (нажатие добавляет контакт и открывает чат); Настройки → Профиль — имя пользователя и адрес сервера.
- **Группы**: «Новая группа» → контакты → название = новое пространство с тем же паролем; каждому выбранному в личный чат уходит одноразовое приглашение с кнопкой «Вступить» (вступление создаёт пространство рядом, не закрывая текущее). Пространства-группы показаны строками в списке чатов, нажатие переключает.

Ограничения (`shortcut:`): справочник доверенный (как в Telegram: сервер может подменить ключ имени — сверяйте код безопасности); без лимитов частоты; отвязанное устройство сохраняет действующий сертификат; работает только открытый аккаунт — остальные дочитывают ящик при открытии (уведомления только открытого), группы видны во всех аккаунтах; приглашение в группу — ссылка в сообщении, а не тихое вступление; принять его можно, пока у создателя открыта эта группа.

## 5. Криптография

| Задача | Решение | Крейт |
|--------|---------|-------|
| Подписи, идентичность | Ed25519 | `ed25519-dalek` |
| Обмен ключами | X25519 + ML-KEM-768 (гибрид, постквантовый) | `x25519-dalek`, `ml-kem` |
| Групповые чаты (до 50) | **MLS (RFC 9420)**, cipher suite `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519` | `openmls` |
| Личные чаты | MLS-группа из 2 человек (единый механизм) — или Double Ratchet (решить в §17) | `openmls` |
| Шифрование файлов | XChaCha20-Poly1305, случайный ключ на файл, ключ передаётся внутри сообщения | `chacha20poly1305` |
| Хеш контента | BLAKE3 | `blake3` |
| Транспорт | TLS 1.3 внутри QUIC (iroh), Noise в Tor/LAN-режимах | `iroh`, `snow` |
| Локальная БД | SQLCipher (AES-256), ключ из Android Keystore / Windows DPAPI / пароль | `rusqlite` + `bundled-sqlcipher` |
| Пароль → ключ | Argon2id | `argon2` |

**Почему MLS:** для групп до 50 человек MLS даёт forward secrecy и post-compromise security, а добавление/удаление участника стоит O(log n). Это стандарт IETF с готовой проверенной реализацией на Rust.

**Порядок коммитов MLS без сервера.** MLS требует, чтобы все участники применяли изменения группы (Commit) в одном порядке. Обычно это делает сервер. У нас:
- Изменения состава группы делают только **админы** группы;
- каждый Commit ссылается на номер эпохи; при конфликте (два коммита на одну эпоху) побеждает коммит с меньшим хешем, проигравший админ автоматически пересоздаёт свой коммит на новой эпохе;
- обычные сообщения не требуют порядка — только коммиты.

Для 50 человек и редких изменений состава этого достаточно.

## 6. Сеть и устойчивость к блокировкам

### 6.1 Транспорты

Сеть многоуровневая: ядро пробует все доступные транспорты параллельно и использует лучший работающий (как «Happy Eyeballs»).

| # | Транспорт | Когда работает | Маскировка | Реализация |
|---|-----------|----------------|-----------|-----------|
| T1 | **Прямой QUIC** (UDP, hole punching) | Обычный интернет | Похож на HTTP/3 | `iroh` |
| T2 | **QUIC через relay-узел** | Жёсткий NAT, CGNAT у мобильных операторов | Похож на HTTPS (relay работает поверх HTTPS/443) | `iroh-relay` — запускается на якоре участника, **не** на сторонних серверах |
| T3 | **TCP/TLS на 443** | UDP заблокирован | Имитация обычного HTTPS, uTLS-подобный отпечаток браузера | `rustls` + собственная обёртка |
| T4 | **Tor** (onion-сервис якоря) | Всё прочее заблокировано | Мосты obfs4 / WebTunnel / Snowflake | `arti-client` |
| T5 | **Локальная сеть** (Wi‑Fi, точка доступа телефона, Ethernet) | Интернета нет совсем | — | mDNS-обнаружение + QUIC |
| T6 | **Bluetooth LE** (позже) | Нет даже Wi‑Fi, люди рядом | — | Нативные плагины Android/ПК |
| T7 | **Офлайн-пакет** («sneakernet») | Полная изоляция | — | Экспорт зашифрованного `.mycel`-файла / серии QR; импорт на другом устройстве |

### 6.2 Обнаружение узлов (без DNS и трекеров)

1. **Из инвайта** — начальный список адресов.
2. **Обмен адресами (peer exchange)** — каждый узел периодически сообщает своим пирам свои текущие адреса (подписанные, с временем). Знает адреса одного — узнаешь всех.
3. **Служебный MLS-канал** — якоря публикуют актуальные адреса и onion-адреса туда.
4. **mDNS** в локальной сети.
5. **Ручной ввод** — «добавить адрес вручную» (IP:порт или onion) на случай, когда всё остальное сломано.

Никаких публичных DHT (mainline BitTorrent и т.п.) по умолчанию: они раскрывают, что вы пользуетесь Mycel. Можно включить опцией.

### 6.3 Почему это трудно заблокировать

- Нет домена — нечего блокировать по DNS/SNI.
- Нет единого IP — адреса узлов это домашние IP участников, их десятки, и они меняются.
- Трафик выглядит как HTTPS/HTTP/3 или Tor с мостами.
- Если интернет «отключили» — работает локальная сеть и офлайн-пакеты.
- Если блокировка частичная (например, работает только «белый список») — достаточно одного участника с доступом наружу: его узел становится мостом для остальных через локальную сеть.

### 6.4 Режим «Параноик»

Переключатель в настройках: весь трафик только через Tor, прямые соединения запрещены (не раскрывать свой IP другим участникам). Медленнее, сильнее садит батарею.

## 7. Доставка и синхронизация сообщений

### 7.1 Модель данных: журнал событий

Каждый чат — это **множество подписанных событий** (сообщение, правка, удаление, реакция, «прочитано», изменение участников). Каждое событие:

- имеет уникальный ID = BLAKE3(содержимое);
- ссылается на 1–3 последних известных автору события (`parents`) — получается DAG, как в git;
- отсортировано в UI по (логические часы Лэмпорта, время, ID).

Плюс: нет единого «главного» узла, порядок восстанавливается у всех одинаково, повторно полученное событие просто игнорируется.

### 7.2 Синхронизация

При встрече двух узлов (любым транспортом) они сверяют, у кого каких событий не хватает, с помощью **range-based set reconciliation** (алгоритм как в Negentropy/Willow): обмен идёт компактными «отпечатками» диапазонов, передаётся только разница. Для чатов на десятки тысяч сообщений это занимает 1–3 раунда.

### 7.3 Доставка офлайн-участникам (store-and-forward)

```
Аня (онлайн) ──► отправляет событие ──► Боря (онлайн): доставлено сразу
                         │
                         ├──► Якорь-1 (ПК Димы): хранит зашифрованную копию
                         └──► Якорь-2 (Raspberry у Кати): хранит копию
Вася (офлайн) ... включил телефон ──► синхронизация с любым якорем/участником ──► получил
```

- Каждое событие отправляется всем онлайн-участникам чата **и** всем якорям.
- Якоря хранят события, пока не убедятся, что получатели их забрали (подтверждения), но не дольше N дней (настройка, по умолчанию 30).
- Якорь видит только шифротекст MLS и ID пространства.
- Если якорей нет, работает «эпидемическая» доставка: любой онлайн-участник группы — естественный хранитель, т.к. у него и так есть копия.

### 7.4 Статусы

`⏱ отправляется` → `✓ доставлено` (квитанция `Delivered` хотя бы от одного чужого устройства) → `✓✓ прочитано` (квитанция `Read` хотя бы от одного: получатель шлёт одну, до последнего чужого сообщения, пока чат открыт и окно видимо). В общем чате ✓✓ = «прочитал хотя бы кто-то».

«Печатает…» / «записывает голосовое…»: эфемерный `SyncMsg::Typing { group_id, voice }` по уже зашифрованным QUIC-соединениям с пирами онлайн (только тем, кто видит эту группу), без хранения, почтового ящика и пуша; не чаще раза в 3 с, без повторов при ошибке. Индикатор гаснет через 5 с без обновлений или сразу с сообщением этого человека.

### 7.5 Уведомления на телефоне

Push-сервисы Google/Apple — это центральные серверы, поэтому:

- **Android:** фоновая служба (foreground service с тихим постоянным уведомлением) держит лёгкое соединение с одним якорем; QUIC keep-alive раз в ~25–60 с. Расход батареи — порядка нескольких процентов в сутки. Опционально — **UnifiedPush** через ntfy на якоре.
- **Режим экономии:** проверка раз в 15 минут через WorkManager.
- **iOS:** без APNs фоновая работа невозможна — сообщения приходят при открытии приложения (см. §15).

## 8. Медиа: файлы, фото, видео, голосовые

### 8.1 Блобы

Любой файл → **зашифрованный блоб**:

1. Генерируется ключ файла (32 байта).
2. Файл шифруется XChaCha20-Poly1305 блоками по 256 КиБ (можно расшифровывать по кускам — стриминг видео).
3. От шифротекста считается BLAKE3-хеш (дерево Bao — проверка каждого куска при скачивании).
4. В чат уходит маленькое событие: `{хеш, размер, mime, имя, ключ, превью, длительность, ...}`.
5. Сам блоб скачивается получателями по запросу через `iroh-blobs` — **с нескольких источников сразу** (у кого из участников он уже есть), с докачкой после обрыва.

Максимальный размер файла — не ограничен протоколом (настройка, по умолчанию 4 ГБ).

### 8.2 Типы медиа

| Тип | Обработка на отправителе | Отображение |
|-----|--------------------------|-------------|
| **Фото** | Удаление EXIF/геометки, сжатие в AVIF/WebP (или «отправить оригиналом»), превью 32×32 blurhash прямо в событии | Мгновенный размытый плейсхолдер → полное фото |
| **Видео** | Опционально перекодирование в H.264/AV1 720p (ffmpeg через `ffmpeg-sidecar`, на мобильных — системный MediaCodec), кадр-превью | Стриминг до полной загрузки |
| **Голосовые** | Запись в **Opus** 24 кбит/с, моно (`opus` / `audiopus`), волна (64 точки) в событии | Плеер с волной, скорость 1×/1.5×/2×, прослушивание с места остановки |
| **Видеокружки** | Квадрат 480×480, до 60 с, H.264 + Opus | Круглый плеер, автовоспроизведение без звука |
| **Файлы** | Как есть | Иконка, размер, прогресс, «открыть в...» |
| **Стикеры/GIF** | WebP/анимированный WebP, общие наборы пространства | Инлайн |

### 8.3 Автозагрузка

Настройки «скачивать автоматически»: по Wi‑Fi / по мобильной / никогда — отдельно для фото, видео, файлов. Голосовые < 1 МБ — всегда.

### 8.4 Кэш и место

- Дедупликация по хешу: один файл, пересланный в 5 чатов, хранится один раз.
- «Очистить кэш» удаляет медиа, которые есть у других (их можно перекачать), но не трогает текст.
- Якоря могут хранить медиа дольше, чтобы телефоны освобождали место.

## 9. Звонки

Фаза 3 (после стабильного обмена сообщениями).

- **Аудио 1:1:** Opus 32 кбит/с поверх QUIC-датаграмм (iroh), шумоподавление `nnnoiseless` (порт RNNoise на Rust), эхоподавление — системное (Android) / `webrtc-audio-processing`.
- **Видео 1:1:** VP8/H.264 через системные кодеки; адаптивный битрейт.
- **Групповые звонки (до ~8 человек):** mesh (каждый шлёт каждому); при больших — якорь-ПК работает как SFU (пересылает пакеты, не расшифровывая; ключи кадров — через MLS, по аналогии с SFrame).
- Звонок — это событие в чате + отдельный медиапоток с ключом, выведенным из текущей эпохи MLS.

## 10. Хранение данных на устройстве

```
mycel-data/
├── mycel.db            SQLCipher: пользователи, устройства, чаты, события, состояние MLS, адреса пиров
├── blobs/              зашифрованные блобы (по хешу: ab/cd/abcdef...)
├── thumbs/             кэш превью (тоже зашифрован)
└── keys/               ключ БД, обёрнутый системным хранилищем (Keystore / DPAPI / Keychain)
```

- Блокировка приложения PIN-кодом / отпечатком; через N неверных попыток — опциональное удаление данных.
- **Резервная копия** (Настройки → «Резервная копия», `mycel_core::backup`): один файл `.mycelbak` — история всех пространств, чей пароль известен на устройстве, и по выбору расшифрованные медиа. Шифрование паролем копии: Argon2id → XChaCha20-Poly1305 в конструкции STREAM (сегменты по 1 МиБ, перестановка и обрезка ломают проверку). **Ключа устройства и состояния MLS в копии нет:** копия отстаёт от группы (пропущенные коммиты не расшифровать), а продолжить с теми же ключами — значит повторить номера сообщений храповика, то есть nonce AEAD, если исходное устройство писало после копии или ещё живо; плюс два узла с одним NodeId. Поэтому восстановленное устройство — новое: новый ключ, без групп, история на месте (пароль пространства = пароль копии). В пространство и к контактам входят заново по приглашению, недостающее досинхронизируется штатно (события дедуплицируются по id). Личные чаты из истории видны до повторного входа только для чтения. Ограничения: свои старые сообщения подписаны прежним устройством и показываются как от другого участника; админ, восстановившийся из копии, админом не остаётся. **Фраза восстановления** (§4.1): 24 слова BIP-39 (256 бит), создаются и показываются один раз в «Резервной копии», хранятся в хранилище ОС; копия «по фразе» шифруется нормализованной фразой вместо пароля (тот же Argon2id), восстановление = файл + 24 слова (подсказка слов, контрольная сумма), фраза становится фразой нового устройства. Ключ устройства из фразы не выводится: тогда восстановленное устройство повторило бы NodeId и ключи храповика (см. выше).
- **Экспорт переписки** — чат как HTML с медиа в папке рядом, без шифрования (с предупреждением).
- **Исчезающие сообщения:** таймер на чат (5 мин … 1 неделя), удаление и у получателей.
- **«Тревожная кнопка»:** быстрое удаление всех локальных данных.

## 12. Дизайн интерфейса

### 12.1 Принципы

1. **Привычно.** Структура как у Telegram/Signal — никто не должен учиться заново.
2. **Сеть видна, но не мешает.** Небольшой индикатор состояния связи, подробности — по нажатию.
3. **Быстро.** Открытие чата < 100 мс, список на 10 000 сообщений — виртуализированный.
4. **Одна вёрстка — все экраны.** Адаптивный макет: на телефоне — стек экранов, на ПК — две/три колонки.

### 12.2 Визуальный стиль

- **Палитра:** тёмная и светлая темы; акцент — «мицелиевый» тёплый янтарный `#E8A33D` на графитовом `#16181D` (тёмная) / молочном `#F7F5F0` (светлая). Свои пузыри — акцентный тон, чужие — нейтральный.
- **Шрифт:** Inter (интерфейс), JetBrains Mono (код в сообщениях).
- **Иконки:** Lucide.

**Основные экраны:**

1. **Первый запуск:** «Создать пространство» / «Вступить по приглашению» (сканировать QR / вставить ссылку) → имя и аватар → PIN.
2. **Список чатов:** закреплённые, непрочитанные, поиск по всем сообщениям (локальный полнотекстовый индекс SQLite FTS5).
3. **Чат:** пузыри, ответы со свайпом, реакции долгим нажатием, правка/удаление, пересылка, закреплённые сообщения, «прыжок к непрочитанному».

5. **Просмотр медиа:** галерея со свайпом, зум, сохранение, видеоплеер.
6. **Профиль контакта:** код безопасности, общие медиа/файлы, «проверить по QR».
7. **Люди:** список участников пространства, роли, «Пригласить» (QR + ссылка).
8. **Сеть (🛰):** понятная карта состояния:
   - «🟢 На связи · 23 участника онлайн · 2 якоря»;
   - активный транспорт: Прямой / Через якорь / Tor / Локальная сеть;

9. **Настройки:** тема, уведомления, автозагрузка медиа, режим «Параноик» (только Tor), режим якоря (для ПК: «держать связь 24/7, хранить сообщения для других до N ГБ»), резервная копия, устройства, PIN, исчезающие сообщения по умолчанию.

## 14. Протокол: формат сообщений

### 14.1 Конверт (то, что видит сеть)

```rust
struct Envelope {
    version: u8,                 // версия протокола
    space_id: [u8; 16],          // ID пространства
    group_id: [u8; 32],          // ID MLS-группы (чата)
    epoch: u64,                  // эпоха MLS
    ciphertext: Vec<u8>,         // MLS PrivateMessage
}
```

### 14.2 Событие (после расшифровки)

```rust
struct Event {
    id: Blake3Hash,              // хеш от остальных полей
    author_device: DeviceId,
    parents: Vec<Blake3Hash>,    // 1..3 последних известных события
    lamport: u64,
    timestamp_ms: u64,           // время автора (только для отображения)
    body: EventBody,
    signature: Ed25519Signature,
}

enum EventBody {
    Text     { text: String, reply_to: Option<EventId>, mentions: Vec<UserId> },
    Media    { kind: MediaKind, blob: BlobRef, caption: Option<String>, reply_to: Option<EventId> },
    Edit     { target: EventId, new_text: String },
    Delete   { target: EventId },
    Reaction { target: EventId, emoji: String, remove: bool },
    Receipt  { up_to: EventId, kind: ReceiptKind },          // доставлено / прочитано
    Typing   { active: bool },                                // эфемерное, не сохраняется
    Call     { call_id: [u8; 16], action: CallAction },
    ChatMeta { name: Option<String>, avatar: Option<BlobRef>, disappearing: Option<Duration> },
    Pin      { target: EventId, pinned: bool },
}

struct BlobRef {
    hash: Blake3Hash,            // хеш шифротекста
    size: u64,
    key: [u8; 32],               // ключ XChaCha20
    mime: String,
    name: Option<String>,
    preview: Option<Preview>,    // blurhash / волна голосового / кадр видео
    duration_ms: Option<u32>,
    dims: Option<(u32, u32)>,
}
```

Реакции: `Reaction` есть в enum с фазы 0, поэтому все клиенты его декодируют. Повтор той же эмодзи шлёт `remove: true` (снимает); итог по сообщению — последнее событие каждого автора на каждую эмодзи. Реакции не будят пушем и не считаются сообщениями. Новый вариант `EventBody` старый клиент postcard не декодирует (неизвестный индекс) — такие события он отбрасывает, поэтому новые варианты добавлять только в конец.

## 15. Ограничения и честные компромиссы

1. **«Совсем без серверов» на практике = «без чужих серверов».** Для надёжной доставки, когда люди не онлайн одновременно, нужен хотя бы один часто включённый ПК участника (якорь). Без него сообщения доходят, только когда отправитель и получатель (или кто-то третий из группы) онлайн одновременно.
2. **Мобильный CGNAT.** Два телефона на мобильном интернете часто не могут соединиться напрямую — нужен relay на якоре. Relay — часть Mycel и запускается одной галочкой.
3. **iOS.** Apple не позволяет держать фоновое соединение без своих push-серверов, а без аккаунта разработчика ($99/год) нельзя установить приложение надолго. Основные мобильные платформы — Android.
4. **Батарея Android.** Постоянное соединение стоит заряда; некоторые прошивки (Xiaomi, Huawei) агрессивно убивают фоновые приложения — понадобится инструкция «добавить в исключения».
5. **Метаданные.** Участники видят IP друг друга при прямом соединении (решается режимом Tor).
6. **Объём.** Каждый участник хранит историю своих чатов; медиа можно выгружать на якоря.
